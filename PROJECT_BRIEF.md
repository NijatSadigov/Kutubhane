# Hədəf Kütüphanə — Project Brief for Design

A briefing document for a designer joining the project. Part 1 describes what
exists and works today. Part 2 describes the two upgrades being planned.

Last verified against the codebase: 2026-09-26, branch `backend-dynamic-categories`.

---

# PART 1 — WHAT EXISTS TODAY

## 1.1 What the product is

A **school library management system**, currently deployed for one customer:
Hədəf STEAM Liseyi (a school in Azerbaijan). It is multi-tenant by design — the
data model supports many schools, each with many physical branches.

It is, right now, a purely **internal operational tool**. Students borrow books,
librarians manage inventory and circulation, managers oversee a school, an admin
runs the platform. There is no social dimension, no cross-school visibility, and
no public identity for any user.

The one public surface is an anonymous landing page showing aggregate counts.

## 1.2 Tech stack

**Backend** — `school-library-system/`, ~3,700 lines of Go

- Go 1.25.4
- Fiber v2.52 (HTTP framework)
- GORM v1.31 + Postgres driver (ORM, `AutoMigrate` — no migration files)
- JWT v5 for auth; bcrypt via `golang.org/x/crypto`
- Runs on **port 8000**. Config from env with dev fallbacks (`JWT_SECRET`, `DATABASE_DSN`)
- Auth: JWT in an **HttpOnly cookie** named `jwt`, with an `Authorization: Bearer`
  fallback. Four middlewares: `IsAuthenticated`, `IsLibrarian`, `IsManager`, `IsAdmin`
- File uploads served statically from `/uploads` (covers as images, e-books as PDFs).
  30 MB body limit. **`uploads/` is gitignored** — files live only on the host disk,
  referenced by URL columns in the DB
- ~140 REST endpoints, all under `/api`

**Frontend** — `library-frontend/`, ~6,500 lines of JSX

- React 19.2, React Router 7.12
- Vite 7.2 (the `rolldown-vite` build), fixed to **port 5180** via `strictPort`
- Tailwind CSS 3.4 + PostCSS
- `lucide-react` for all icons
- `axios` for the API layer
- **No component library** (no MUI, shadcn, Radix, Headless UI). Every control is
  hand-rolled Tailwind. There is one shared `Modal.jsx` and everything else is
  built inline in the page files
- **No state manager** (no Redux/Zustand/React Query). Two React Contexts:
  `AuthContext` and `LanguageContext`. Data is fetched per-page with `useEffect`
  and held in local `useState`
- **No test suite** and no Storybook

**Database** — Postgres 18, local. Schema is generated by GORM AutoMigrate at boot.

## 1.4 The data model

**Tenancy chain:** `School` → `Branch` → everything else. Almost every table
carries a `branch_id`. This is the single most important structural fact about
the system: **the catalog is per-branch, not global.** Two branches of the same
school have entirely separate book records, separate authors, separate genres.

**Identity:** one `User` table (email, password hash, role string) with a
role-specific profile table keyed on `UserID`:

| Role | Profile table | Scope |
|---|---|---|
| `admin` | *(none)* | the whole platform |
| `manager` | `Manager{Name, SchoolID}` | one school (many managers allowed per school) |
| `librarian` | `Librarian{Name, SchoolID, BranchID}` | one branch |
| `student` | `Student{Name, BranchID, Grade, ClassGroup, BirthDate, LoanLimit}` | one branch |

Note that **`Student` already carries `Grade` (int) and `ClassGroup` (string)** —
e.g. grade 7, class group "A". Little uses them yet, but they exist.

**Catalog:**

- `Book` — title, ISBN, call number, language, CEFR level, publication year,
  edition, page count, physical description, notes, cover URL, e-book URL.
  Category links are **nullable foreign keys**, not free text: `AuthorID`,
  `PublisherID`, `TopicID`, `GenreID`, `FrequencyID`
- `BookCopy` — a physical copy with its own `TrackingNumber` (the barcode/label
  the librarian sticks on the book), plus `ConditionID` and `StatusID`
- **Dynamic category tables**, all branch-scoped and fully CRUD-able by the
  librarian: `Author`, `Publisher`, `Topic`, `Genre`, `Frequency`, `CopyCondition`,
  `CopyStatus`, `LoanStatus`, `ReservationStatus`

**Status tables have two fields: a `Name` the librarian can rename freely, and a
`Code` that is fixed and used by the logic.** Codes: copy = `AVAILABLE` /
`LOANED` / `RESERVED`; loan = `ACTIVE` / `RETURNED`; reservation = `PENDING` /
`APPROVED` / `REJECTED` / `COMPLETED` / `EXPIRED`. A designer must never assume a
status label is a known string — the school may have renamed it, in any language.

**Circulation:**

- `Loan` — student + copy, issue date, due date, nullable return date, status, description
- `Reservation` — student + copy, request date, `PickupDays`, nullable
  `PickupDeadline`, status, description
- `ReadingLog` — the reading diary: loan + student + page reached + optional note +
  timestamp. Reading speed is derived from the timestamps across entries
- `BookRequest` — a student asking for a book the branch doesn't own
  (free-text title + author + note; plain status string)
- `RegistrationToken` — a branch-scoped invite link with label, expiry, revoke
  flag and use count

**Policy fields:** `Branch.LoanLimit` (default 5), `Branch.MaxPickupDays`
(default 7), and an optional `Student.LoanLimit` override.

## 1.5 What each role can do today

### Student

- **Home** — overview of their activity
- **Catalog** — browse and search the branch's books; filter by CEFR level,
  language and availability; see cover art; open an e-book PDF if one is attached
- **Reserve** a book (the system picks a genuinely free copy automatically)
- **My Books** — current loans with due dates, history of returned books
- **Reading diary** — per loan, log the page reached plus a note; see a progress
  bar and the history of entries
- **Stats** — books read, pages read, reading speed (pages/day), progress bars
  for books currently being read
- **Request a book** the library doesn't have — a title + author + note form,
  also offered automatically when a search returns nothing
- Self-register through an invite link from a librarian

### Librarian (one branch)

Seven nav tabs: Home, Books, Reservations, Requests, Loans, Members, Settings.

- **Home** — KPI strip: total books, total copies, available copies, active
  loans, pending reservations, overdue, members
- **Books** — full CRUD on books and on individual copies; cover image upload;
  e-book PDF upload; **CSV bulk upload**
- **Loans** — a prominent "Give Book" modal: pick student by name → pick book →
  pick an available copy, with a live "currently holds X of limit Y" readout.
  Edit and return loans
- **Reservations** — approve or reject; approving stamps a pickup deadline;
  expired reservations release their copy automatically
- **Requests** — the queue of student book requests; fulfil or reject
- **Members** — the student roster; per-student reading stats modal; generate
  and revoke registration invite links
- **Settings** — CRUD on every dynamic category and status list for the branch

### Manager (one school, several allowed per school)

Five tabs: Branches, Students, Requests, Librarian Tracking, Branch Library.

- Create, edit and delete branches of their school (creating one auto-seeds its
  status tables)
- Create, edit and remove librarians
- View all students across the school
- Edit the school profile
- **Librarian tracking** — a table of per-librarian workload: branch, books,
  copies, active loans, pending reservations, pending requests, students
- **Branch Library workspace** — read-only view into any branch of their school
  (Books / Loans / Reservations sub-tabs). Deliberately read-only: managers do
  not do librarian data entry
- Every `/manager/*` endpoint resolves the school from the JWT, never from the
  request body, and returns 403 for anything outside it

### Admin (platform)

- CRUD on schools, branches, librarians and managers
- Full super-admin reach over everything

### Public (no login)

- A landing page at `/` with platform-wide and per-school aggregate counts —
  schools, branches, students, books, books read, pages read. **Counts only, no
  personal data.** Logged-in visitors get a "go to my dashboard" link

## 1.6 Design system as it stands

This is what exists; treat it as a starting point, not a constraint.

**Brand**

- Primary blue `#1B9DD9`, hover/darker `#1580B5`
- Secondary accent: Tailwind `sky-*`
- Light info tints `#E0F2FE` / `#7DD3FC` / `#BAE6FD`; dark info text `#075985`
- **Semantic red is retained deliberately** — errors, overdue items, delete and
  danger actions. Reserved/rejected badges use pink `#FCE7F3`
- Colours are written inline in the JSX. There are **no Tailwind theme tokens**,
  no CSS custom properties, no design tokens of any kind
- The wordmark currently renders as the text "Hədəf". `public/logo.png` is
  absent; drop a real logo there and it appears automatically

**Layout patterns in use:** left sidebar nav with lucide icons on dashboards;
KPI card strips; dense data tables; modals for every create/edit action; tab bars
with an underline indicator.

**Dark mode** — partially present. Some components have `dark:` variants, many do
not. Not a shipped feature.

**Internationalisation — this is a hard constraint.**

The UI ships in **three languages: Turkish (tr), Azerbaijani (az), English (en)**.
It is a hand-rolled system: `i18n/translations.js` holds ~1,167 flat keys per
language; `useTranslation()` gives `{ t, lang, setLang }`; the choice persists to
`localStorage`; missing keys fall back to Turkish and then to the key itself.
`t('key', {vars})` does `{var}` interpolation. A `LanguageSwitcher` sits in every
header.

Practical consequences for design:

- **Every string in a mockup needs a key.** Nothing can be hardcoded
- Azerbaijani and Turkish run **substantially longer than English** — often 30–50%.
  Buttons and labels must survive that; fixed-width controls sized to English will break
- Azerbaijani uses `ə`, `ğ`, `ı`, `ö`, `ş`, `ü`, `ç` — the chosen typeface must
  cover extended Latin
- The current Azerbaijani strings were AI-translated and have not had a native
  speaker's pass

**Accessibility** — no audit has been done. Contrast, focus states, keyboard
navigation and screen-reader semantics are all unverified.

## 1.7 Known gaps and rough edges

- The newest backend features — borrow limits, pickup deadlines, branch policy
  settings — **have no UI at all.** The endpoints exist and are tested; nothing in
  the frontend calls them. A librarian cannot set a loan limit or a pickup window
  from the app, and a student who hits a limit sees a generic error rather than an
  explanation
- Three book covers are generated placeholders rather than real cover art
- Admin dashboard CRUD has never been verified end-to-end in a browser
- ~20 cosmetic lint warnings
- Nothing has been pushed to a remote; the project lives on one machine

# PART 2 — WHAT IS PLANNED

Two separate upgrades. They pull in opposite directions — one opens the product
outward, one deepens the internal tooling — and they should be designed as
distinct surfaces.

## 2.1 Upgrade A — the social layer ("Letterboxd for books")

**The ambition:** stop being only an internal library program. Become a place
where readers keep a profile, rate and review what they read, follow each other,
build lists, and discover books through other people.

**This is the piece to design first.**

What already exists that the social layer can build on:

- Every student has an identity, a branch, a grade and a class group
- A complete reading history: what was borrowed, and when it was returned
- A reading diary with page-level progress, timestamps and free-text notes
- Derived reading statistics: books read, pages read, pages per day
- Book records with cover art, author, genre, topic, CEFR level, page count
- A public, anonymous landing page already exists as a front door

What does not exist and will have to be invented:

- Any notion of a **profile** that another person can look at
- **Ratings and reviews** — the diary has private notes, nothing shareable
- Any **social graph** — no following, no friends, no groups
- Any **feed**, notification system, or activity stream
- **Lists / shelves** beyond the implicit "currently borrowed"
- Any identity that survives outside a single branch

### Structural problems a designer should know about

**1. The catalog is branch-scoped, and this fights the whole concept.**
`Book` rows belong to a branch. The same novel held by two branches is two
unrelated rows with different ids, possibly different titles, spellings and
authors. A social layer needs *one* page per work that everyone's activity
attaches to. Somewhere there has to be a shared "work" concept sitting above the
per-branch physical copies. This is the central architectural question of the
whole upgrade, and the design will imply an answer to it whether or not it says
so explicitly.

**2. The users are schoolchildren.** A social network among minors is not the
same product as Letterboxd. Whatever gets designed needs an answer for: who can
see a given student's profile — classmates, the whole branch, the whole school,
everyone? Can a librarian or manager moderate reviews? Are real names shown, or
handles? Is following mutual-consent or open? Are there reading statistics that
would be uncomfortable to display publicly — "read 2 books this year" sitting next
to a classmate's 40? This wants deciding at design time rather than retrofitted;
it shapes every screen.

**3. Reading volume is small.** A school branch has tens of students and tens of
books. A feed designed for Letterboxd's density will look abandoned here. The
design needs to work when there are three reviews in total.

**4. There is no notification infrastructure** — no email sending, no push, no
in-app notification model. Anything the design assumes will have to be built.

### Open questions worth resolving with the designer

- Is the social layer visible on the public internet, or only to logged-in members
  of the school?
- Does it span schools? Can a Hədəf student follow a reader at another school?
- Do librarians and managers have social profiles, or only students?
- Is this a new top-level surface, or a new tab inside the existing dashboards?
- Does the existing dashboard aesthetic — dense tables, KPI strips, sidebar nav —
  carry over, or does the social side deserve a different visual language? It is a
  consumer product bolted onto an admin tool; those usually want to look different

## 2.2 Upgrade B — the "dərslik" system (classroom textbook distribution)

**The scenario:** at the start of each school year the school issues textbooks to
classrooms. Class 7-A has some number of students; based on the subjects that
class takes, the librarian hands out a set of textbooks. At the end of the year
the books come back.

**Why it cannot reuse the existing loan system:**

| | Current library loans | Dərslik |
|---|---|---|
| Borrower | an individual student | a **class** (7-A) |
| Initiated by | the student, on demand | the librarian, in bulk |
| Timing | any time, all year | once at the start of the year |
| Duration | weeks | the whole academic year |
| Return | one book, whenever | the whole set, at year end |
| Driven by | what the student wants to read | the subjects on the class timetable |
| Choice | the student chooses | no choice; it is issued |

So this is a second, parallel circulation mode. The natural shape is a bulk issue
and a bulk return against a class, driven by a subject list, rather than one
transaction per student per book.

**What exists that helps:** `Student.Grade` and `Student.ClassGroup` are already
on the model. `BookCopy.TrackingNumber` gives every physical copy a barcode.
`RegistrationToken.Label` already uses "7-A sınıfı 2024" as its example — the
class-cohort idea is latent in the system.

**What does not exist:** any `Class` entity, any notion of a subject, any academic
year or term, any bulk-issue or bulk-return operation, and any concept of a loan
whose counterparty is a group rather than a person.

**Design questions this raises:**

- Is the book issued to the class as a unit, or to each student individually with
  the class as a convenience wrapper? This determines who is accountable when one
  copy goes missing in June
- How does a librarian handle the end-of-year return of ~30 books at once — scan
  every barcode, or mark the set returned and flag the exceptions?
- What happens to a student who joins or leaves mid-year?
- Damaged and lost textbooks — how are they recorded and chased?
- Does a student see their textbooks in the same "My Books" view as library loans,
  or somewhere separate? They are a different kind of object in a student's mind
- Do textbooks appear in the catalog at all, or are they a separate inventory?
- Do textbooks count against the borrow limit? (They should almost certainly not)
- Does any of this touch the social layer? (Almost certainly not — nobody reviews
  their chemistry textbook)

## 2.3 Suggested sequencing

The stated order is: **design the social layer first**, then the dərslik system.
That order makes sense — the social layer is the one that changes what the product
*is*, and it carries the unresolved structural question about branch-scoped versus
shared book identity. The dərslik system is additive internal tooling and can be
designed against the existing visual language once that language is settled.
